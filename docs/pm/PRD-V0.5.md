# PiX-Read V0.5 产品需求文档（负责人：主 agent / 迭代负责人）

> 上游：`docs/pm/PRD-V0.4.md`（R6–R10 已交付：阅读现场恢复、AI 结论入库、笔记复用与注入、知识地图结构联动、笔记规模化可用；`.pix-read/notes.json` 是笔记唯一事实源，`.pix-read/reader-state.json` 是易失现场）。
> 本轮范围约束：只做「本地论文阅读 + AI 辅助」主线。不做论文下载、元数据抓取、DOI/BibTeX、云同步、多标签、多文档对比、自动摘要、暗色主题、多色笔、公式识别、OCR。
> 迭代代号 **R11–R15**（V0.5 共 5 轮）。需求编号从 **N73** 起。
> 档件约定（沿用 V0.4）：需求档 `R<n>-req.md`、评审档 `R<n>-review.md`（需求评审 + 设计评审 + 代码审查）、设计档 `R<n>-design.md`（含定稿修订）、开发档 `R<n>-dev.md`（改动清单 + 真实命令与结果 + 逐条自评 + 未验证事项）。

## 1. 战略判断：V0.4 之后剩下的三处断层

V0.2 解决「读得进」，V0.3 解决「读有所得」，V0.4 解决「读得回、用得上」。以「每天用它读论文」的标准重新审视产品，剩下的不是功能数量问题，而是三处结构性断层：

1. **结构与阅读位置脱节 —— AI 不知道你在哪一节。**
   知识地图已经能算章节页码范围、章节笔记数与阅读位置（R9），但「当前章节」这件事只活在地图内部：阅读器不显示它，`<reading_context>` 里也没有它。用户问「这一节的核心假设是什么」时，agent 只拿到一个页码，必须重新读一遍正文，还可能读错范围。论文是强结构文本，结构语义应当是全产品的一等公民：界面可见、上下文可见、导航可用。

2. **读完之后带不走东西 —— 产出仍是半成品。**
   笔记能导出，但导出物是一份按文档分组的平铺清单。对「读完一篇论文，写一段可复用的文献笔记」这个真实终点，用户还得自己重组章节、区分摘录与 AI 结论、补上阅读进度。**产出物应当由产品生成**，而不是让用户二次加工。

3. **资产在各面上不一致 —— 看不见，也信不过。**
   资料库树知道阅读进度，却不知道哪篇有笔记；笔记面板知道文件内容，却不知道文件在外部被改过。资产必须在每个面上都有可见、可信的表达；「唯一事实源」不仅要写进文档，还要在界面上兑现。

**V0.5 主题：读得深、带得走、看得见。**
让结构语义贯通阅读器与 AI（R12），让每篇论文能带走一份结构化阅读报告（R13），让笔记资产在资料库与面板上可见可信（R14）；用一轮收口修复（R11）清掉 V0.4 遗留缺陷并补上验证基础设施，用一轮全量审查（R15）做零外溢收口。

## 2. 迭代路线（R11–R15）

| 迭代 | 名称 | 一句话 | 依赖 | 性质 |
| --- | --- | --- | --- | --- |
| R11 | 收口修复 | 修 V0.4 遗留缺陷（Esc 语义越界、摘录反馈被无关滚动吞掉）、取证脚本启动清理、回归断言补齐、可复跑数据面烟测入口 | — | 修复 / 基建 |
| R12 | 章节语义贯通 | 当前章节在阅读器可见、进 `<reading_context>`、可上一节/下一节跳转；无 outline 时全程静默降级 | R9 | 功能 |
| R13 | 阅读报告 | 每篇文档导出结构化 Markdown 阅读报告（章节分组 + 摘录/AI 结论 + 备注 + 阅读进度） | R9、R10 | 功能 |
| R14 | 资产贯通 | 资料库树的笔记徽标、笔记文件外部改动感知、阅读器侧章节笔记入口 | R6、R9、R10 | 体验 |
| R15 | 全量审查 | 全仓库代码审查与修复：正确性 / 一致性 / 失败路径 / 死代码 / 文档漂移 | R11–R14 | 质量 |

依赖是真实的：R12 复用 R9 的 `buildChapterRanges` 唯一派生（不允许第二份区间算法，也不允许引入 LLM 生成结构）；R13 复用 R10 的导出管道与 R6 的现场数据（报告里的阅读进度只能来自 `reader-state.json` 与渲染层持有的 `pageCount`）；R14 的树徽标复用 R10 的计数口径与 R6 的树内展示位；R15 必须在 R12–R14 全部落地之后执行，否则审查对象不完整。

## 3. 资产分层（V0.5 增量）

| 路径 | 性质 | 损坏 / 缺失时的行为 |
| --- | --- | --- |
| `<工作区根>/.pix-read/notes.json` | **用户资产**（唯一事实源） | 报错、绝不覆盖、用户显式决策（既有逃生口，口径不变） |
| `<工作区根>/.pix-read/notes.md` | 导出产物（全量平铺） | 全量覆盖写（既有口径不变） |
| `<工作区根>/.pix-read/reports/**`（R13 新增） | 导出产物（每篇文档一份结构化报告） | 全量覆盖写；目录缺失即创建；**不参与读取**，删掉不影响任何功能 |
| `<工作区根>/.pix-read/reader-state.json` | **易失状态**（现场记忆） | 静默降级并允许重建（既有口径不变） |

一句话原则不变：**资产宁可停下来问用户，状态宁可自己重来，产物随时可以重生成。**

## 4. 版本级反需求（跨迭代写死）

1. 不做论文下载、元数据抓取、DOI/引用解析、BibTeX 管理、云同步、多设备。
2. 不做 LLM 自动摘要 / 自动写笔记 / 自动打标签：任何 AI 产出必须由用户显式动作触发，且必须能回看（笔记或报告）。**R13 的报告是确定性产物，不得调用 LLM。**
3. 不做向量检索、全文索引服务、知识图谱、双链、自动术语表。
4. 不做多标签、多文档对比、暗色主题、多色笔、压感、公式识别、OCR。
5. 不引入新运行时依赖（含 d3 / markmap / fuse 等）；不改 `packages/*`（pi 内核）；不改 electron-builder 配置。
6. 不做笔记静默注入：任何进入上下文的内容必须在 composer chips 上可见、可移除（R8 口径不变）。
7. 不改变 `.pix-read/notes.json` 的格式与写入协议（`version: 1`）；导出产物不得混入事实源；`.pix-read/` 之外的仓库内容不被产品写入。
8. 不做向后兼容层；不写未被调用的死代码；不为「看起来高级」加动画。

## 5. 工程红线（对每一轮的子代理生效）

1. `cd pix && npm run check`（vue-tsc + 主进程 tsc + preload tsc）必须 **0 error**，这是唯一工程门。
2. 禁止 `any`；禁止内联动态 import（`await import()` / `import("x").T`），全部顶层 import。
3. UI 文案中文；注释只写约束、不写流水账；风格向同文件看齐；Vuetify 用法照抄仓库内既有写法（本仓库无 `vuetify_guide/`）。
4. 子代理不运行 `npm run build` / `npm test` / `npm run package` / `npm run dev`；不执行任何 git 写命令（`git status` / `git diff` / `git show` 只读可用）。提交由负责人（主 agent）在流水线末端完成。
5. 主进程新增 IPC 必须有入参校验与中文错误；渲染层失败路径不得静默；渲染层不得自行拼接存储路径（路径一律由主进程从资料库根派生）。
6. 主进程新增导出/写盘必须落在资料库根内的 `.pix-read/`（越界一律 `outside`），原子写，损坏不覆盖。
7. 取证纪律：每轮动工前先跑基线离屏取证（`PIX_SHOT_ROOT=<临时目录>/pix-v05-r<N>-base`），开发后跑验收取证（另一临时目录）；`MANIFEST.json.failure === null`、退出码 0、既有场景与断言零缺失；**新增/变更的 UI 必须有对应场景与截图，且不得删除既有场景**。冻结字面的有意变更必须在本轮需求档中显式登记（写明改哪一条、为什么、旧断言如何更新）。
8. 每一轮 `packages/*`、`pix/package.json` 的依赖字段、lockfile 必须零改动（R11 允许新增一个 `scripts` 条目，见 N75）。
9. 离屏取证脚本 `pix/scripts/ui-shot.mjs` 是唯一 UI 回归基线：stub 的 `pixApi` 面必须与 `pix/src/main/preload.ts` 保持一致；两个取证进程不得并发（同一端口 5199）。
10. 仓库内不得留下临时脚本、临时产物、调试日志；一次性脚本写在 `%TEMP%` 并在用完后删除。

## 6. 每轮流水线（对子代理可见的执行契约）

```
需求(PM) → 需求评审(挑刺) → 需求定稿 → 设计(架构) → 设计评审(挑刺) → 设计定稿
   → 开发(契约面 → UI 面) → 代码审查 + 独立复验 → 修复 → 终验(check + baseline/after 离屏 + 越界核对) → 负责人提交
```

- 判定证据固定五种（与 R10 相同）：【走查】只读代码与 `git diff`；【check】`cd pix && npm run check`；【烟测-渲染】纯函数离线烟测；【烟测-主进程】数据面烟测（R11 起为仓库内可复跑脚本）；【离屏】`ui-shot.mjs` 截图 + `MEASUREMENTS.json` 断言组。
- 每条需求必须标注判据来源；无判据的需求不得进入设计档。
- 需求评审与设计评审必须给出 must-fix 清单（可为空，但必须逐条说明「为什么不是 must-fix」）；must-fix 未销账不得提交。

## 7. 版本成功判据

1. **修复零回归**：R11 的三个缺陷各有独立断言；112 张既有截图与 153 条既有测量零缺失；`npm run check` 每轮 0 error。
2. **结构语义贯通**：阅读器能看出当前章节；`<reading_context>` 在可解析时含 section（不可解析时逐字节等于旧格式）；上一节/下一节可用且与翻页互不干扰；地图、阅读器、AI 三处对「当前章节」的判断来自同一份派生。
3. **报告可带走**：每篇文档能导出结构化报告；报告内容与 `.pix-read/notes.json` 逐条一致（字节级可判）；无笔记 / 无章节 / 无现场数据时行为明确且不报错。
4. **资产可见可信**：资料库树能看出哪篇文档有笔记、有多少条；笔记文件被外部修改后面板给出非阻塞提示且不静默覆盖；面板计数与文件始终一致。
5. **全量审查收敛**：R15 的审查清单全部有结论（已修复，或登记为不修并写明理由）；`packages/*` 与依赖零改动；仓库无死代码、无临时产物。
